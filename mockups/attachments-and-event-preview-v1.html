§1 · הסימן — שורה שאומרת שיש עליה מסמך

ADR-0152 §6c gave a row a note mark and fought for its 13px on the app's most crowded line. `lib/attachments.ts` already ships `attachmentCountsByHost` / `attachmentCountFor` — written for exactly this and never called by anything, which is report (b) in one line: the count exists, nothing renders it. The only question a drawing can answer is whether the row survives a second glyph, because a booked event's meta line already carries a place name, a confirmation code, a sync badge and the note mark.

These render the app's own rule, not a hopeful version of it. `eventMetaParts` already drops the place name when a row has a code and a mark (`showPlace = placeName && !(code && (hasMark || placeInTitle))`, ADR-0152 §6c) — so A and B below show the place gone, which is what the shipped app draws. The one case the doc mark actually changes is C: a code and a document but no note. Today `hasMark` counts notes only, so the place stays and the line has to hold four things. That is the whole code change — `hasMark` learns to count both — and C is the drawing of why it is needed.

This is report (a), and it is smaller than it sounds. `DocumentChip` renders a title span and one button, and that button detaches. §6 · הכותרת המורמת — המסך שבשבילו הפיצ׳ר קיים

ADR-0174 does not mention this surface, and it is the one the feature exists for. The lifted hero (ADR-0160) is Trip mode's read for what is happening now and next. It already reads `איפה`, `פתק` with a count of what it is not showing, the booking reach and `הסדרה` — and it shows no documents at all. You are standing at the gate, the flight is `now`, and the boarding pass attached to it is invisible on the one surface built for standing at the gate.

Three constraints this surface has and no other does. (1) It is the `--on-dark` ramp in both themes (ADR-0158 §15), so `.doc-chip`'s `--ink` 4% wash is invisible here — the same trap `SettleControl`'s `board` density exists for. (2) It is content-sized and bounded (ADR-0148 §1: head pinned, ONE scroller, foot pinned), so anything added competes for that scroller — ADR-0160 §8 already measured a two-way group split 92px over at 360×640. (3) `אחר כך` is one line by construction (§12): its type carries no id, so nothing can hang off it, and that stays true here.

The trap ADR-0160 already recorded, and it is ours too. The hero reads a booked event's notes from the BOOKING as well as the event, because a booked event is server-materialized and has no client id (§I / ADR-0172 §7). Attachments have exactly that shape, so the hero resolves them through the SAME `resolveHostContext(hostContexts, { kind: 'event', id })` call the notes already go through — one call, both content types, so the hero and the day row cannot disagree about what a point carries.

The three treatments, head to head. H1 is a `HostDocuments` section like every other read surface. H2 is one chip per document in the point's existing `hero-acts` row — the row whose own comment reads "every way out of a point, in ONE row" — opening the viewer directly. H3 is the mark alone, which is the cheapest and reaches nothing.

Measured: –
Recommended: H2 — a chip per document in the point's own `hero-acts` row. Four reasons, and the first is the one that decides it.
(1) It is one tap to the file, and that is what this surface is for. H1 is a tidy section and it is still one tap to the file — but it spends a label line and a block on saying "מסמכים" to someone who is holding a phone at a gate. H3 spends nothing and reaches nothing, which is exactly today's defect one surface over.
(2) It needs almost no new CSS, and the little it needs is a DENSITY. `.hero-act`'s base rule — `rgba(255,255,255,0.07)` under `--on-dark` — is already in the stylesheet and used by nothing: every call site today passes `.loc` (teal) or `.time` (amber). A document is neutral by rule 4, so the neutral base is exactly right and was waiting for it. What is genuinely new is one `.doc` modifier that caps the width and lets the title ellipsise, because a document title is the only thing in that row that is stored content. That is the shared chip gaining a density, not a second chip.
(3) The row's own semantics already cover it. `.hero-acts` is "every way out of this point" — `במפה`, `ניווט`, `להזמנה`. Opening the document is a way out of the point, reached the same way, so it belongs in the row rather than beside it.
(4) `הבא בתור` gets it for free, because `HeroLift` already renders `<Where point={next} />`. And `אחר כך` gets nothing, also for free, because `HeroThen` carries no id — §12's condition holds without a line of code.
What it costs, and this is the number to weigh: –. The fourth chip wraps the row onto a second line, which is the state ADR-0160 §O measured its way into once already (three chips at 247px against 308px on a 360px phone). Wrapping is the correct behaviour here rather than a defect — `flex-wrap` is on that row deliberately as the safety net — but it means the honest claim is "one wrapped line", not "free".
And `canLift` learns to count it. A point whose only depth is an attached document currently answers "nothing to lift" and takes the rebuff — the board would refuse to open onto the one thing it now has to show.

§8 · הקריאה ההפוכה — מצויר פעם אחת כדי להראות את המחיר

Out of scope, and drawn anyway because "we are deliberately not doing this" is worth one drawing rather than one sentence. ADR-0173's own Consequences flag it: once a document can be attached, a row on the documents screen can no longer be read as "belongs to the trip and nothing else" — and the screen says nothing about where it is attached. A is what ships today; B is the smallest honest fix (one meta line, the same `.map-m` grammar the place row uses), and it is a third feature — it needs a reverse index (`attachmentsForDocument`), a way through to each host, and a decision about what a document attached to five hosts says.
