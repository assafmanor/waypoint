Mode

Watch the close, not the open. In BEFORE the card never translates and the node is torn out on the frame onClose runs — every sheet, dialog, picker and the search overlay snaps shut. Enter-slow / exit-instant is the single most common reason an app reads as unfinished, and today it is app-wide.

Open a variant

Each variant arrives the way its shape implies: the sheet rises from the edge it came from, the dialog has no edge so it is summoned in place, and full replaces a screen so it arrives like a screen — the same grammar as G2's forward push, which is why the two must share one direction rule.

variant enter exit
sheet translateY 100%→0, --t-base / --ease-arrive reverse, --t-quick / --ease-exit
dialog scale .96→1 + opacity, --t-base scale→.97 + opacity, --t-quick
full translateX inline-end→0, --t-base reverse, --t-quick
scrim opacity, on its own channel opacity, --t-quick
Exit is briefer than entrance, on purpose. Symmetric timings feel sluggish on the way out — you have already decided to leave. --t-base in, --t-quick out.

Proofs

Reduced motiona `closing` state must still resolve with no animation
Directionthe same CSS must mirror — `translateX` is physical

Thememotion rides tokens, so it must survive the flip
The reduced-motion case is a real bug waiting to happen. The exit timer must read 0, not the token — read it from the token and the overlay stays mounted for 140ms of nothing, still covering the screen and still holding focus. Correct by construction: derive the hold from the same media query that kills the animation.

Where it lands

One change in ui/primitives/Modal.tsx + modal.css. Every overlay in the app inherits it — sheets, ConfirmDialog, RowManageSheet, BookingSheet, EventForm, SearchOverlay, the document viewer. The state machine is open → closing → unmounted, and the pattern is already in the repo: .toast stays mounted and animates both ways off a .show class.

One constraint that does not move. ADR-0132 §2 leaves the Map's chrome reclaim un-animated because animating it relayouts the split mid-flight. The overlay's arrival must not be made to cross-fade against the chrome disappearing — they are two different surfaces and only one of them may move.

Mode

.body's fade covers in-trip tab content only. Every full-screen .app surface renders with no entrance at all — /login, the zero state, /new, the born screen, /join, /trips, both settings screens. Every transition in the two journeys the owner named is one of these.

Navigate

Forward and back must not look the same, or the motion carries no information — it becomes decoration you learn to ignore. And the pair is deliberately asymmetric: the arriving screen travels the full width, the one you leave recedes only ~22% and dims. A symmetric slide reads as a carousel; an asymmetric one reads as depth, which is what "deeper into the app" means.

direction arriving leaving
forward from inline-end, 100% → 0 to inline-start −22%, opacity → .55
back from inline-start −22%, opacity .55 → 1 to inline-end 100%

Proofs

DirectionRTL is the app's base; LTR must mirror for free
Reduced motioncollapses to the hard cut, which is correct
RTL is the trap, and it is the one frontend/CLAUDE.md already documents. translateX is physical; there is no logical transform. In RTL, inline-end is the left edge, so a forward push enters from −100%. Hence one --dir sign on the shell and translateX(calc(var(--dir) * 100%)) — not a mirrored copy of every keyframe.
Two things it must compose with. Direction comes from nav state, never from reading history (ADR-0090 — and traversal is lint-blocked). And it must be mutually exclusive with the mode switch's data-switching window, or a Plan→Trip flip that also changes route runs two transitions over each other.

press and hold — mouse down counts as a touch here

Mode

tokens.css kills the mobile tap-flash app-wide, justified in its own comment by "every tappable surface has its own :active / hover / focus-visible feedback". Counted: ~16 :active rules in the entire frontend. Most buttons acknowledge a tap with nothing at all.

Phone-primary (ADR-0017) makes this correctness, not polish: there is no hover state to fall back on, so for the frame before the target appears the app has told the user nothing. Cheapest feel-per-line change in the codebase.

Why scale and not colour

A colour press-state needs a per-surface table — the app has a dark glowing board, paper cards, amber tints, violet chrome — and it would spend from the semantic colour budget (amber = time, teal = location, violet = plan) on chrome. Scale composes with every surface and needs no table.

target press why
small (chip, icon, nav) scale .97 + brightness .96 legible at 32–44px
large (card, tile, CTA) scale .985 a big surface at .97 reads as collapsing
timing --t-quick / --ease-standard must land inside the same frame budget as the tap
Two sizes, not one. Toggle to AFTER and hold the CTA, then the nav item — the ratio is what should read as constant, not the transform. One value for both is the version that looks broken on the card.

Proofs

Reduced motionpress feedback disappears entirely — is that right?
Themebrightness() must not invert on dark
An open question, deliberately left open. App.css's global rule kills transition with !important, so under reduced motion the press state snaps rather than eases — which is arguably correct (instant acknowledgement is still acknowledgement). But brightness(.96) darkens on a dark theme too, where "pressed" may want to be lighter. Judge both on a device before wiring a second rule.

Status: proposal, not a decision — adoption needs an ADR covering Modal's enter/exit contract, the shell transition's direction source, and the press-feedback rule, plus the two token additions (--stagger-step, --ease-arrive). What this file cannot settle: real durations on a real device under a real thumb. Everything here is judged on a desktop with a mouse; the numbers are starting points. Order matters: G1 and G3 change how the whole app feels for a contained diff, and G1 is the primitive the two set-piece journeys then build on — so they land before motion-trip-birth-v1.html and motion-join-v1.html.
