**Status:** ACCEPTED (living index — update it in the same change whenever a mockup is added, or a listed one is superseded/ships)

Promotes: **the three-phase entry condition** (a tap that is passed straight through, a provisional second press that is the only thing taken from Google, and a commit past the slop), with a log naming what Google _would_ have received at each step; **the arbitration as a capture-phase guard rather than ADR-0122 §4's "both listen and the loser bails"** — that precedent is safe only because the sheet's losing drag renders nothing, where Google's pan writes the camera on the first move; **§A2's geometry**, which is where the brief's expected central problem dissolved (`.map-pane` is `bottom: var(--sheet-h)`, so the canvas and the sheet's drag region never share a pixel and were never going to fight — the real competitor is Google's double-tap, which is enabled); **§B's two anchors side by side with the thumb drawn**, settling centre-anchoring on the grounds that the tapped point sits under the finger and that ADR-0129 §1 already refused a lateral move bundled into a zoom; **§C the dot tier crossing live** on a real `[data-pins]` attribute so the shipped degradation css does the work, which also draws ADR-0123's invariant that a pin's SIZE does not change under zoom while its TIER may. **Two numbers the file moved:** the direction (down zooms in — the design had reasoned _up_ from the sheet's "up means more", and a finger overruled it) and the sensitivity (0.18 → 0.5 across two rounds). **Read §D's warning before re-tuning:** this file's canvases are 260px and 214px against ~501px shipped, and because the sensitivity is a **share**, the same constant is twitchier here than in the app — so §D's table is what to calibrate against, not the feel of this file. The canvas is a scaled grid, not Google's tiles, so nothing here speaks to how it reads over real imagery at 60fps.
