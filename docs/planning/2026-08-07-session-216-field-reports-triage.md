## 1. Discrepancies found during revalidation

Both worth a future session's attention before it starts building:

- **Field-report #10 collides with a same-day decision.** `backlog.md`'s Map panel section (the "pin number is the index of a STOP, not of a place" entry, dated 2026-08-06 — the same day as HEAD) shows ADR-0121 §6 was **just amended** to make "a place visited twice consumes two stop numbers" the explicit, intentional design, not an oversight: _"A day is a sequence of stops and a place visited twice is two of them, so the stops are numbered... the airport becomes 3."_ That is Screenshot C's exact case (Ben Gurion `1`, Vienna `2`, Keflavik `4`). So field-report #10 is not a bug against a long-standing design — it is the owner reversing an ADR-0121 §6 amendment that shipped, at most, hours before the report. The future build session should amend §6 again and explicitly note the reversal in the ADR, per CLAUDE.md's "don't let behavior drift silently" rule; check whether the §6 amendment's own reasoning (a genuine revisit must still count twice) is compatible with "one logical connection, one stop" before touching the code — the two are meant to coexist (a derived arrival+departure of one connection collapses; a true later revisit does not).
- **Field-report #1's underlying mechanism already exists and was also just shipped.** ADR-0168 (`the-search-answers-on-the-canvas.md`, same day) and its implementation in `frontend/src/lib/useMapCamera.ts:92` ("A settled set of search results arrived (ADR-0168 §1) — pan to them...") already do exactly what the owner is asking for — but for the Map tab's own search overlay. `useMapCamera` is a shared hook, not Map-tab-only, so the first thing the bug-fix session should check is whether the booking/event place-selection errand (`PlacePicker` / the `usePlaceErrand` family in `frontend/src/lib/places.ts` and `booking-draft.ts`) is wired to the same hook or renders through a separate path. If it's the same hook, this is a narrow wiring gap; if it's a parallel path, it's a real regression against ADR-0168's promise. Not diagnosed further here — that is the build session's job.

No other claim in the handoff (code file, ADR number, or "still true" assertion) failed revalidation. Confirmed directly against current HEAD: `frontend/src/lib/place-label.ts:6` (no IATA field, comment says so), `frontend/src/screens/Map.tsx:3021` (`allUsages.length === 0` branch precedes the search-results branch), `frontend/src/lib/readiness.ts:73-78` (`reachesDestination` does destination-string substring matching, not route/location truth), `frontend/src/ui/NoteComposer.tsx:143-146` (Enter commits, Shift+Enter breaks a line, comment cites the current rule), `frontend/src/lib/notes.ts:256` (`Date.parse(createdAt)` with no finite-date guard), `frontend/src/lib/booking-draft.ts:209` (`roundTrip: false`), `frontend/src/ui/BookingSheet.tsx` (full `ChoiceGrid` on the category step at :819-820; `useHostNoteCount` imported for a count only, not `notesForHost`, so existing notes are not rendered on edit), `docs/design/design-language.md:127` (body 14.5px), `frontend/src/ui/primitives/FilePicker.tsx` (thumbnail/tile preview card only, no full-view surface).

## 3. Owner decisions vs. open questions

**Treat as settled requirements** (owner-provided, not hypotheses — a future session does not need to re-litigate these, only build them):

- Map search camera reacts when the **settled result set** arrives, never waiting for a tap (#1).
- Booking title must not be required for **any** booking type where place/provider/route/type gives a usable fallback — not hotel-only (#9).
- The typography complaint is **app-wide**, not one screen (#3).
- Document preview must show the **full** selected document before Save, not a thumbnail (#19).
- Suggested booking times are **auto-prefilled and remain editable** — the mechanism is approved; the exact values are not (#11).
- "Airport initials" means the real **IATA code** (#7) — not a string derived from the display name.
- The round-trip-still-missing bug is specifically the **Plan Home readiness screen** (#5).
- One-way vs. round-trip must be an **explicit user choice**; the app must never default to one-way (#8).
- Enter must insert a **newline** in the current note; creating a separate note is a distinct, explicit action (#13).
- One logical layover/connection = **one visible stop number**; a place genuinely revisited later must still get its own number (#10).

**Open — recommendations only, not decisions** (a future product/design session must resolve these; do not build them as if settled):

- Flexible-time semantics (`exact` / `not-before` / `not-after`): the owner leans toward `not-before` for check-in but has not signed off a complete model (#16, #17, #18).
- Category-picker-after-selection shape: "collapse + Change" is the working hypothesis; the owner's own wording was tentative (#2).
- Hotel provider copy: `הוזמן דרך` is a leading suggestion, not approved Hebrew (#12).
- Existing notes in booking edit: they must be visible (settled, and is itself the defect in #14) — but whether editing them is inline or via the shared note-editor surface follows the existing Notes decisions and is not yet chosen (#14).
- Exact per-booking-type default clock values (hotel check-in/out, etc.) — not defined; only the prefill-and-editable mechanism is approved (#11).
- Airport-only Places search: phrased "if possible" by the owner — verify Google Places' actual capability/cost on the exact request path used before promising a filter (#6).
- A replacement type scale: no approved numbers exist yet — do not add `+2px` everywhere as a shortcut (#3).
