# Architecture Decision Records (ADRs)

This is the project's memory. Docs elsewhere describe _what is true now_; ADRs preserve _what we decided and why_, so decisions are never silently reversed or re-litigated.

## What earns an ADR

Any decision that is expensive to reverse or that a future contributor would otherwise question: product scope calls, platform/tech choices, data-model shapes, collaboration rules, integration boundaries. If you'd want to know "why is it like this?" six months from now, write one.

## Process

1. Copy the template below into `NNNN-short-title.md` (next number).
2. Fill it in. Keep it short — a screen, not an essay.
3. Set **Status**: `Proposed` → `Accepted` → (later) `Superseded by NNNN`.
4. Add it to the index below.
5. Never edit an Accepted ADR's decision; instead write a new ADR that supersedes it.

## Template

```markdown
# NNNN — Title

**Status:** Proposed | Accepted | Superseded by NNNN
**Date:** YYYY-MM-DD

## Context

What forces are at play? What problem are we deciding on?

## Decision

What we chose.

## Consequences

What becomes easier, harder, or constrained as a result.

## Alternatives considered

What else we weighed and why we didn't pick it.
```

| [0135](0135-a-place-becomes-an-event-or-a-booking.md) | **A place becomes an event or a booking, and the CONFIRMATION CODE decides which.** The epic's remaining product hole: a place added from the map can only ever be an **idea** — `refEntriesFor` builds ways in to references that already exist, and there is no create branch. **The session's first design was rejected in place, and both halves of the verdict generalise.** It hung two entries, `＋ אירוע` and `＋ הזמנה`, in the same grey `.map-ref` box as the references; the owner read it as _"cluttered and very amateur looking"_ — correctly, because a `.map-ref` ends in a chevron since it **goes** somewhere and a create goes nowhere, so four equal grey rectangles turned the expanded row into a summary, a navigation list and a **command menu** at once. And: _"maybe the user doesn't choose one or the other but the code understands instead."_ **(1) One action, in a control the tab already owns** — the block keeps its reference list and gains a footer holding `.map-addmaybe`, the same pill `＋ אולי` uses, on the same neutral `--cta`; what separates it from a reference row is shape and weight, not a new colour. One scoped size change, a **floor** rather than a taste: 44×44 here (ADR-0017) instead of the 29px chip a dense result row wants. **(2) The code decides the entity.** `EventForm` gains one collapsed `Collapsible` line, `יש קוד הזמנה?` — empty, the save creates a soft event; filled, it creates a **`Booking`** and its linked event through the shipped `bookingEventFields`. "Event or booking?" is the app's question, not the traveller's; _do I have a confirmation number?_ is a fact about the world. And it is **ADR-0011's own sentence** ("hard = real commitment (flight, reservation code)") finally being read by something rather than applied by hand. The booking's **type** derives from the **form's own category field** via a new `CATEGORY_TO_BOOKING_TYPE` (the inverse of the shipped map) — the form's category, not the place's, because it already leads the form (ADR-0109 §11), already defaults from the picked place through the icon's group (ADR-0038), and is therefore a control the user already has, so the fix for a wrong guess needs no second picker. The guess is **stated** in a quiet line that moves with the category pill rather than asked. The category picker and the `IconPicker` are untouched, and the line is **create-only**: typing a code into an existing event would be a conversion, not a field. **App-wide by owner's call**: the same gap exists on every authoring surface, and a map-local sheet would have been a third one. **(3) Hard/soft is derived, and "the code decides the entity" is NOT "the code decides the kind"** — a coded booking takes `bookingDefaultKind`, so a dinner reservation stays **soft** exactly as authoring it in `BookingSheet` does today; deriving `hard` from a code would have made every restaurant ripple-immune. **(4) The originating idea is consumed** through `verbs.schedule`, unchanged (ADR-0027 §2) — including on the coded path, since a booking's linked event produces the same duplication. **Unless there are two ideas**, where nothing is consumed: two ideas are two intentions, and the block cannot tell them apart (an idea entry reads `על המדף · <day>` and nothing else), so it does not guess. **And it is explicitly NOT the errand run backwards:** the errand exists because leaving a `Modal` loses it, and here nothing is left — the form opens over the map, on the map's own tab, which already hosts `BookingSheet`. The precedent is ADR-0134 **§9**, the target with no `returnTo` because it starts on its own destination. What the errand IS owed is one hook call (`usePlaceErrandReturn<EventFormDraft>('event', 'map', …)`), session 165's "a host that renders a form owes it a way back". **Measured, and the finding was not the one it looked for:** the rejected menu cost +92px against a plain row's 73px and this design costs +56px; the form itself goes 482px → **560px** with the line closed (+78px, ~16%), which is what every host of `EventForm` pays and is the app-wide call priced rather than buried — but the block **already** overflows the `half` sheet on a 360 with two references (186px against 153px) before this phase adds anything, so a `scrollIntoView({ block: 'nearest' })` on selection ships with it.
